Conn3x closes the gap between creating infrastructure and configuring it: one plan, one state and one apply for the cloud and the servers in it. Today it does that for Linux, and for Windows Server in preview.

Where it's going is further than that. Anything you'd do with Terraform, OpenTofu, Ansible, Chef or Puppet, you should be able to do with Conn3x, and this page is the route there.

This page says what's planned and in what order. None of it has a date, and nothing here works until a release says it does. The words stable, preview, experimental and planned mean the same here as everywhere else in the docs; [Maturity labels](/reference/maturity) says what each one promises. The [release notes](https://github.com/conn3xorg/conn3x/releases) are the record of what has shipped.

## Today

- **Adopt servers you already run.** `import = true` on a step takes over what a host already has instead of creating it. Since v0.9.0 that covers 21 Linux modules, from `file` and `package` to `cron`, `mount` and the firewall rules, since v0.10.0 seven Windows modules, since v0.11.0 all eight and the PostgreSQL and MySQL steps, since v0.15.0 seventeen Windows modules, since v0.16.0 twenty-one, the forest, domain controllers and domain members among them, and `provider::conn3x::import_id` adopts what a shared circuit manages. [`conn3x generate step`](/reference/cli/generate-step) reads an object on a host and writes its step for you. The first plan shows only where the host and your circuit disagree, so nothing changes until you've read it. Steps take a `lifecycle` block too: `prevent_destroy`, `ignore_changes`, `replace_triggered_by`, and preconditions and postconditions, with OpenTofu's own messages. [Adopt servers you already run](/guides/adopt-servers) walks through a whole server.
- **A slow host doesn't hold up the rest.** Since v0.9.0, [`strategy = "per_host"`](/reference/circuits/steps#per-host) on a circuit lets each host run its own steps in order without waiting for the others, and its handlers run as soon as that host is done. The default is still lockstep. Since v0.10.0, [`when`](/reference/circuits/steps#when) runs a step on only the hosts where a condition is true, and [`run_once`](/reference/circuits/steps#run_once) runs it on one.
- **Databases.** Since v0.11.0, `postgresql_database`, `postgresql_role`, `mysql_database` and `mysql_user` steps make databases and accounts with exact grants, through the client on the host, and passwords never travel as plain text.
- **Changes that put themselves back.** Since v0.11.0, `confirm_after` on a `file`, `template`, `ufw` or `firewalld` step has the host undo the change on its own if Conn3x can't log in again afterwards.
- **Linux hosts.** Conn3x configures Rocky Linux, RHEL, AlmaLinux, Fedora, Debian and Ubuntu. Every change to Conn3x is tested on Rocky Linux 10, Fedora 45, Ubuntu 24.04 and Debian 13.
- **Windows hosts, in preview.** Windows Server 2022 and 2025, over OpenSSH, from the same plan as everything else. Twenty-five `windows_*` modules cover PowerShell scripts, reboots and waits, Windows Update, files, folders and access rules, registry values, services and features, users and groups, firewall rules, MSI packages, scheduled tasks, IIS sites and app pools, a network interface's DNS servers, a new Active Directory forest and a child domain inside it, joining a domain, adding a domain controller, and the OUs, groups and users inside it. `conn3x drift` checks these hosts the way it checks Linux ones. The [azure-windows-server](https://github.com/conn3xorg/conn3x/tree/main/examples/azure-windows-server) example builds a Windows Server VM on Azure and configures it in one plan. Windows as a whole is in preview. Since v0.15.0, 15 of these modules are out of experimental; the other 10 are experimental, which each one's [page](/modules/windows_update) says: their arguments may change between releases. [Preview and experimental together](/reference/maturity#preview-and-experimental-together) explains how the two fit.
- **127 official circuits.** Web servers, databases, monitoring, Kubernetes, DNS, VPNs, hardening, identity, detection and response, vulnerability scanning, compliance tracking, CI runners and a private AI stack, each pinned to a release and tested on the systems its page lists. [IIS](/circuits/iis) and [Active Directory](/circuits/active-directory) are for Windows Server, and they're experimental, like the modules they use. The [circuit catalogue](/circuits) has them all.
- **The [Circuit Builder](https://conn3x.org/build).** Pick a distribution and the circuits you want, fill in a short form, and get a config that's ready to plan. k3s, Zabbix, FreeIPA and Velociraptor take their hosts by role, servers on some and agents or clients on others. It can also create the servers on AWS, Azure, Google Cloud or DigitalOcean, in the same plan. That part is in preview, and on Azure it means Linux hosts, with Windows still to come. It won't let you pick two circuits that fight over a port, and CI validates every circuit it offers, alone and in a set of realistic builds. Your picks live in the page address, so you can share a build as a link. Some circuits aren't in it yet, IIS and the network-device ones among them, and the [Builder page](https://conn3x.org/build#not-yet) names each with the reason.
- **AI you can account for.** A private AI stack from circuits: [Open WebUI](/circuits/openwebui) and [Ollama](/circuits/ollama) for chat that stays on your servers, a [LiteLLM](/circuits/litellm) gateway with per-team keys and budgets, [Presidio](/circuits/presidio) masking personal data before a model sees it, and [Langfuse](/circuits/langfuse) keeping a trace of every call.
- **Your playbooks come with you.** `conn3x convert ansible` rewrites the tasks it can prove and marks the rest with the reason. Since v0.9.0 it converts a local role into a circuit directory too, with `-role`, and since v0.11.0, with `-out`, a play's roles convert along with it, `include_role`, `import_role` and their `meta/` dependencies included. Since v0.12.0 that covers `tasks_from`, a role in a `loop`, `win_updates`, and the `community.postgresql` and `community.mysql` database tasks.
- **Any OpenTofu provider.** Conn3x runs the same providers OpenTofu does, so whatever creates your servers today can keep doing it. Four clouds are tested end to end, on real servers: [AWS](/tutorials/aws), [Azure](/tutorials/azure), [Google Cloud](/tutorials/google-cloud) and [DigitalOcean](/tutorials/digitalocean) each have a tutorial, and we've applied Builder configs on all four. Google Cloud has a [BigQuery](/tutorials/bigquery) example too. The rest work the same way, and we haven't run them ourselves.
- **Checks, reports and assistants.** Since v0.10.0, [`conn3x lint`](/reference/cli/lint) checks a circuit's own code for what the circuit grader marks down, [`-report`](/reference/cli/apply#-report) on `apply` and `drift` writes a JSON report of the run, and [`conn3x mcp`](/reference/cli/mcp) lets an assistant look things up over the Model Context Protocol without running a plan. All three are experimental.
- **Runs on** Linux and macOS, on amd64 and arm64, and since v0.10.0 on Windows, as `conn3x.exe`, which is experimental.

## Now: Windows at scale

You can build a small domain now, and fill it. [windows_ad_forest](/modules/windows_ad_forest) makes a new forest, [windows_dns_client](/modules/windows_dns_client) points a server's DNS at it, and since v0.7.2 [windows_domain_membership](/modules/windows_domain_membership) joins a server to the domain and [windows_ad_domain_controller](/modules/windows_ad_domain_controller) promotes a member to another domain controller. Since v0.7.3, [windows_ad_ou](/modules/windows_ad_ou), [windows_ad_group](/modules/windows_ad_group) and [windows_ad_user](/modules/windows_ad_user) keep what lives inside the domain, run on a domain controller, and a hand edit in Active Directory Users and Computers shows up as drift. The [azure-domain](https://github.com/conn3xorg/conn3x/tree/main/examples/azure-domain) example builds a forest on one Windows Server 2025 VM, joins a second to it, and creates a `Lab` OU with a user and a group she's in, all from one config. We've promoted that second VM to a domain controller on Azure too. Since v0.11.0, [windows_ad_domain](/modules/windows_ad_domain) adds a child domain to the forest, and a group can take members from any domain in the forest, or one it trusts. We've tested a child domain, and a root-domain group with a child-domain user in it, on Azure. Members from across a forest trust haven't been tested yet. Since v0.16.0, `windows_ad_forest`, `windows_ad_domain_controller`, `windows_domain_membership`, `windows_ad_ou`, `windows_ad_user`, `windows_user` and `windows_group` are out of experimental; `windows_ad_domain` and `windows_ad_group` aren't yet.

The Active Directory lab works. One config builds two domain controllers and two member servers on Azure, with the OUs, users and groups inside the domain, and shows every step in the plan first, reboots included. [circuit-active-directory](/circuits/active-directory) does it by role, and the [lab tutorial](/tutorials/active-directory-lab) walks through a run, with what it costs and how to tear it down. We built it from nothing three times in a row, and each time the second plan was empty and both domain controllers replicated cleanly. Since v0.9.0 the [azure-windows-fleet](https://github.com/conn3xorg/conn3x/tree/main/examples/azure-windows-fleet) example builds a domain controller and up to five IIS web servers from one apply, and `conn3x_host` reports each Windows host's `build` and `update_revision`, so you can see which ones are behind on updates.

The work now is Windows at scale: many hosts in one apply rather than four, and the `windows_*` modules moving from experimental to preview, with arguments you can count on between releases. Since v0.16.0, 22 of the 25 have, and the [readiness page](https://github.com/conn3xorg/conn3x/blob/main/docs/windows-readiness.md) says what the other 3 still need.

## Next: network devices over their own CLI

Switches, routers and firewalls, configured in the same plan as the hosts behind them.

The first three are out, and they work through community OpenTofu providers rather than Conn3x's own connection: [RouterOS baseline](/circuits/routeros-baseline), [OPNsense VLANs](/circuits/opnsense-vlans) and [Proxmox VE network](/circuits/proxmox-network). They're [experimental](/reference/maturity): each was tested on a virtual image, not hardware, and its page names the image and the provider. Next is talking to devices over their own CLI, starting with Arista EOS. The first EOS modules, `eos_config`, `eos_hostname` and `eos_vlan`, are in Conn3x since v0.9.0, and since v0.10.0 `eos_interface` and `eos_user` join them, with one commit per switch per apply. All are experimental, tested against cEOS-lab and not yet on hardware; [Network devices](/network-devices) explains how they work and what they need from the switch. Since v0.17.0 it talks to Juniper Junos too: `junos_config`, `junos_hostname`, `junos_vlan`, `junos_interface` and `junos_user`, with a dry run before every commit and one `commit confirmed` per device, tested on vJunos-switch and not yet on hardware. VyOS and classic Cisco IOS come next.

## Done: Ansible roles from Galaxy

`conn3x convert ansible` handles tasks, plays and, since v0.9.0, one local role at a time with `-role`. Since v0.11.0 a role's `meta/` dependencies convert with it, and since v0.16.0 `-role geerlingguy.nginx` fetches a role from Galaxy for you and converts it. The rule is the same as ever: what the converter can prove, it rewrites, and everything else it marks with the reason. See [Convert a role](/guides/migrate-from-ansible#convert-a-role).

## Done: ad-hoc commands

Since v0.16.0, [`conn3x run`](/reference/cli/run) runs one command or module on the hosts an inventory pattern matches, without a circuit and without state, over the same SSH connections and host keys a plan uses. Since v0.17.0 its patterns take Ansible's subscripts, such as `webservers[0]`.

## Then: a web UI

A self-hosted, open-source web app for teams: run plans and applies from a browser, see each run's output and history, approve a plan before it applies, schedule drift checks, and keep credentials and access per project. Think [Semaphore UI](https://github.com/semaphoreui/semaphore) or AWX, built for one plan that covers the cloud and the servers in it.

## Toward full IaCC

Infrastructure as code and configuration: the five steps above are the start of it. These are the rest, in the order we expect to build them. A few slot in between those steps, and each one says where.

- **The rest of OpenTofu, on host steps.** Most of it is here. Since v0.8.0 a step takes `import` and a `lifecycle` block, so you can adopt a running server and put `prevent_destroy` on the step that matters. Since v0.9.0 import covers the other Linux modules, adopts through a shared circuit you call as a module, and `conn3x generate step` reads what's on a host and writes the step for you. Since v0.10.0, seven Windows modules take `import`. What's left is import on the other Windows modules, and `conn3x generate step` for Windows hosts. It goes alongside Windows at scale.
- **Inventory and host data.** Half of this is here. Since v0.16.0 a circuit takes its hosts from an Ansible inventory, with its `group_vars` and `host_vars`, through [`provider::conn3x::inventory`](/reference/circuits/hosts). Still to come: looking a value up by host, group, environment or a common default, the way Hiera or Chef attributes do.
- **Rolling updates and orchestration.** Part of this is here. Since v0.15.0 a circuit can [roll out in batches](/reference/cli/apply#batches) and stop once too many hosts fail, [`-limit`](/reference/cli/plan#-limit) runs it on some hosts only, and [`on`](/reference/circuits/steps#on) runs a step on another host. Running a step on one host is here since v0.10.0, as `run_once`, and since v0.16.0 a command step runs on the machine Conn3x runs on with `on = "controller"`. Still to come: naming a set of steps as a task, then chaining tasks into a plan, the job Bolt does for Puppet. It builds on ad-hoc commands and comes before the web UI, which runs these as jobs.
- **Servers that keep themselves right.** Puppet and Chef put a server back every half hour without anyone asking. Conn3x tells you about drift today; here it fixes it on a schedule from the web UI, and keeps every run's report and every host's facts somewhere you can search. A pull mode, where the host asks for its own config, comes after, with its own design.
- **Encrypted secrets you can commit.** Ephemeral variables and write-only files already keep secrets out of state. This adds encrypted variable files, like Ansible Vault or Chef's encrypted data bags, sharing the web UI's way of holding credentials.
- **Compliance, tests and policy.** Checks that only report, the way InSpec does, so an auditor gets an answer and nobody's server changes. A test command that starts containers for a circuit, like Test Kitchen or Molecule. And policy that reads a plan, host steps included, before anything applies: that one works today with Conftest, as [Check a plan against your policies](/guides/policy-checks) shows, and a built-in check would come later.
- **Your own modules, and your Chef and Puppet code.** A way to write a module without changing Conn3x itself. Converters for Chef cookbooks and Puppet modules that behave like `conn3x convert ansible`: rewrite what they can prove, mark the rest with the reason. And a registry for circuits, with versions and search.
- **Runs that start on an event.** An alert fires or a webhook arrives, and the right job runs, as Event-Driven Ansible does.

## Alongside: more circuits

New circuit rounds wait while the work above gets built, unless people ask. Requests still count: the last batch came from lists people sent us, so keep them coming.
